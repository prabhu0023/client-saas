# Feature Spec — Staff-Created Appointments (Dashboard)

> Per-feature spec for DoctorDesk. Source: staff need to book appointments from
> the portal (walk-ins, phone calls), not only via the patient WhatsApp flow.
>
> **Status:** ⬜ ready to build
> **Companion:** `product-requirements.md` (SoT) §6 data model, §7 core behaviors.

---

## 1. Context & goal
Today appointments are created only by the WhatsApp booking flow
(`created_via='whatsapp'`). Staff have no way to book from the portal for a
walk-in or a patient who phones the clinic. Add a dashboard action to create an
appointment for a patient — finding an existing patient by typing their name (or
phone), or adding a new patient inline — then booking a real available slot.

**Goal:** from the staff dashboard, a staff member can create an appointment:
search/select an existing patient (or add a new one), pick a doctor + a real
available slot, and confirm — creating the appointment with `created_via='portal'`,
using the same atomic no-double-booking path as WhatsApp.

**Non-goals (v1):** no force-booking outside availability (real slots only); no
editing patient demographics beyond name/phone at creation; no recurring
appointments.

---

## 2. Compliance gate
Not a new clinical-messaging surface — this is staff booking within their own
clinic. Standard tenancy applies (clinic-scoped, RLS, requireStaff). N/A beyond
that. Patient name/phone are PII — handled under the existing patient-data posture.

---

## 3. Requirements
- **R1 — Patient search.** A type-ahead searches the clinic's `patients` by
  `full_name` **and** `wa_phone` (partial, case-insensitive), clinic-scoped,
  returning matches with name + phone to disambiguate. **Acceptance:** typing a
  name or a phone fragment lists only this clinic's matching patients; no
  cross-clinic results.
- **R2 — Add new patient inline.** If the patient isn't found, staff enter a new
  patient (full_name required, wa_phone required in E.164, optional DOB/notes);
  on save a `patients` row is created `(clinic_id, wa_phone)` and selected.
  **Acceptance:** creating a new patient persists the row and continues into
  booking; a duplicate `(clinic_id, wa_phone)` reuses the existing patient rather
  than erroring.
- **R3 — Doctor + real slot selection.** Staff pick a doctor, then a day, then an
  available time generated by the **existing** `generateSlots` (clinic tz, slot
  length, availability rules/exceptions, minus existing appointments). Only real
  open slots are offered. **Acceptance:** the slots match what the WhatsApp flow
  would offer for the same doctor/day; past/booked/off slots never appear.
- **R4 — Atomic create.** Booking goes through the existing `book_appointment`
  RPC (the `btree_gist` exclusion constraint is authoritative) with
  `created_via='portal'`. If the slot was taken between display and submit, the
  create fails gracefully and re-offers slots — never double-books.
  **Acceptance:** two staff booking the same slot → one wins, the other is
  told to pick again; the appointment appears on the dashboard immediately.
- **R5 — Tenancy + roles.** Only authenticated staff of the clinic
  (`requireStaff()`) can search patients and create appointments; all queries
  clinic-scoped. **Acceptance:** a cross-clinic patient search/create returns
  nothing / is rejected; test asserts isolation.
- **R6 — Dashboard entry point.** A "New appointment" action on the dashboard
  opens the flow; on success returns to the dashboard with the new appointment
  visible. **Acceptance:** the created appointment shows in the day view.

---

## 4. Design
### 4.1 Fit with existing architecture
Pure additive portal feature. Reuses:
- `src/lib/availability/slot-generation.ts` (`generateSlots`) for R3 — same
  function the WhatsApp flow uses.
- `src/lib/booking/book.ts` → `book_appointment` RPC for R4 (atomic). The RPC
  already upserts the patient by `(clinic_id, wa_phone)`; for portal booking the
  patient is pre-selected/created, so pass the resolved `patient_id`/phone.
- `requireStaff()` (`src/lib/portal/auth.ts`) + the RLS-scoped read pattern
  (`src/lib/portal/appointments.ts`) for the portal path (RLS, NOT service role —
  staff are authenticated).
- `created_via='portal'` already exists in the appointments enum.

**Likely NO new migration** — all tables exist. IF a patient-search index or
anything schema-level is genuinely needed, it MUST be numbered **015+**
(migration 011 is applied; the onboarding feature in flight claims 012–014). Add
a trigram/`ilike` index on `patients.full_name` only if search is slow; prefer
`ilike` first.

### 4.2 Flow / UI
Dashboard "New appointment" → modal/route:
1. **Patient step:** type-ahead (name/phone). Results list → select. "Not found?
   Add new patient" → inline form (name, phone E.164, optional DOB/notes) → create.
2. **Doctor step:** pick a doctor in the clinic.
3. **Slot step:** pick day → available times from `generateSlots`.
4. **Confirm:** create via `book_appointment` RPC, `created_via='portal'`;
   on `slot_taken` re-offer the day's slots (mirror the WhatsApp recovery).
5. Return to dashboard; appointment visible.

### 4.3 Open questions
- Patient search as a server action with debounce vs. a search route — pick the
  pattern that matches the existing portal (server actions, per inbox/availability).
- Reuse the inbox/availability form + error-state style (ReplyForm pattern) for
  consistency.

## 5. Tasks
### T1 — Patient search (server action + UI)
- **Scope:** clinic-scoped `ilike` search over `full_name` + `wa_phone`; type-ahead UI.
- **Acceptance:** R1, R5 (isolation test).
- **Deps:** none.

### T2 — Add-new-patient inline
- **Scope:** create-patient server action (upsert by clinic_id+wa_phone, E.164 validation); inline form.
- **Acceptance:** R2 (new persists; duplicate reuses).
- **Deps:** T1.

### T3 — Doctor + slot selection (reuse generateSlots)
- **Scope:** doctor picker; day→time from `generateSlots`.
- **Acceptance:** R3 (slots match WhatsApp flow).
- **Deps:** T1.

### T4 — Atomic create + dashboard entry
- **Scope:** wire `book_appointment` RPC with `created_via='portal'`, slot_taken recovery; "New appointment" dashboard action + return.
- **Acceptance:** R4, R6; no double-booking under contention.
- **Deps:** T2, T3.

### T5 — Tests
- **Scope:** search isolation; new-patient create; slot parity with WhatsApp; atomic/slot_taken; role enforcement.
- **Acceptance:** full `npm run build` + `npx vitest run` green incl. all existing tests.
- **Deps:** T1–T4.

---

## 6. Verification
- `npm run build`; `npx vitest run` (existing stay green).
- Slot parity: assert portal slots == `generateSlots` output for a doctor/day.
- Atomic: two concurrent portal creates for one slot → one booked, one slot_taken.
- Tenancy: clinic A staff cannot find/create for clinic B.

## 7. Rollout & done
- No migration expected; if added, 015+. `created_via='portal'`.
- Docs: add to PRD §4 booking group; board; Done-log.
